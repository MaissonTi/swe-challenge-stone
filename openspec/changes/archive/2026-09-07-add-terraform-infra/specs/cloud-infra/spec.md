## Purpose

Provisions, via Terraform, the AWS infrastructure needed to persist the
application's data (the `Users` and `Products` DynamoDB tables and the
API's access identity to them) as real, reproducible infrastructure —
not only simulated in LocalStack for local dev.

## ADDED Requirements

### Requirement: Users table provisioned via Terraform
The system SHALL provision, via Terraform, a DynamoDB table for users
with primary key `email` and a GSI `byUserId` that allows looking up a
user by `userId` (the JWT `sub` claim), matching the schema already
used by the application against LocalStack.

#### Scenario: Applying the configuration creates the users table
- **WHEN** an operator runs `terraform apply` against an AWS account
  with the required credentials and variables configured
- **THEN** a DynamoDB table exists, named per the configured variable,
  whose partition key is `email` and which has a GSI `byUserId`
  queryable by `userId`

### Requirement: Products table provisioned via Terraform
The system SHALL provision, via Terraform, a DynamoDB table for
products with primary key `productId` and two GSIs: `byCategoryActive`
(partition key combining category and active status, sort key on name
for ordering/prefix filtering) and `byActive` (partition key on active
status alone, same sort key), matching the schema already used by the
application against LocalStack.

#### Scenario: Applying the configuration creates the products table
- **WHEN** an operator runs `terraform apply` against an AWS account
  with the required credentials and variables configured
- **THEN** a DynamoDB table exists, named per the configured variable,
  whose partition key is `productId` and which has the GSIs
  `byCategoryActive` and `byActive`, both with the name-based sort key
  used for ordering and prefix filtering

### Requirement: Least-privilege API access to the tables
The system SHALL provision, via Terraform, a dedicated IAM role/policy
for the API's access to the `Users` and `Products` tables (and their
indexes), restricted to the item-level read/write and query actions
the application needs (`GetItem`, `PutItem`, `UpdateItem`,
`DeleteItem`, `Query`), granting no `Scan` and no access to any other
account resource.

#### Scenario: Generated policy does not exceed what's needed
- **WHEN** the IAM policy generated by Terraform is inspected
- **THEN** it authorizes only `GetItem`, `PutItem`, `UpdateItem`,
  `DeleteItem`, and `Query` on the ARNs of the `Users`/`Products`
  tables and their indexes, and grants no `Scan` nor any action on
  resources outside those two tables

### Requirement: Environment-parameterized configuration
The system SHALL allow region, environment, and table names to be
parameterized via Terraform variables, and SHALL expose the identifiers
of the provisioned resources (table names/ARNs, IAM role ARN) as
outputs, for consumption by the application's configuration.

#### Scenario: Outputs available after apply
- **WHEN** `terraform apply` completes successfully
- **THEN** the `Users` and `Products` table names/ARNs and the access
  IAM role ARN are available as Terraform outputs

#### Scenario: Same module provisions distinct environments
- **WHEN** an operator applies the configuration twice with different
  values for the environment/name variable
- **THEN** each apply provisions a set of resources with distinct
  names, without colliding with each other
